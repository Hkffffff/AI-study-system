# 08 MVP 开发路线

原则：**垂直切片**，每个里程碑都交付一个前后端打通、可以实际使用的功能；不要先把所有后端基础设施一次做完。

## 0. 开工前

- [ ] 准备至少一家 Provider 的 API Key
- [ ] 准备一组**真实样例**（约 10 道题：数学手写、408 选择题、PDF 扫描页、模糊照片、一页多题），用于 M4 以后的 Prompt 调试和验收

## 1. 里程碑总览

| 里程碑 | 主题 | 交付后可以做什么 | 迁移脚本 |
|---|---|---|---|
| M0 | 项目骨架 | 前后端都能启动，页面显示布局和健康状态 | — |
| M1 | 学习空间 + Subject | 创建和切换「数学一」「408」，并维护各自的 Subject | V1 |
| M2 | 归档 + 文件上传 | 上传照片和 PDF 到归档，浏览并查看原件和 PDF 页 | V2 |
| M3 | 题目管理 | 从图片或 PDF 页建题、标注角色、查看列表和详情（还没有 AI） | V3（含复习预留列） |
| M4 | AI 分析（单个 Provider） | 一键分析，看到识别和分析结果，版本可以追溯 | V4 |
| M5 | 确认流程 + 多模型 | 审阅、确认、修正、驳回；可信度；知识点；在 GPT 和 Claude 之间切换 | — |
| M6 | 题目级对话 | 针对某道题和 AI 流式对话 | V5 |
| M7 | 打磨与交付 | 日常可用：打包、备份、Prompt 调优、文档同步 | — |

**MVP 完成 = M0–M7 全部完成。**

## 2. 各里程碑详情

### M0 项目骨架

- **后端**：Maven 项目（Java 21、Spring Boot 3.x），按模块建空包，`common` 中实现错误模型（ProblemDetail）和分页；配置 Flyway 和 MySQL 连接；`server.address=127.0.0.1`；健康检查接口。
- **前端**：Vite + Vue 3 + TS + Element Plus + Router + Pinia；`AppLayout`（顶栏空间切换器占位、侧栏导航，AI 助手和学习画像显示为禁用）；axios 实例和错误提示；开发代理 `/api`。
- **工程**：`git init`；`.gitignore`（`.env`、`data/`、构建产物）；`.env.example`；`docker-compose.yml`（MySQL 8）；README 中写明启动步骤。
- **验收**：一条命令启动 MySQL，前后端都能启动；页面显示布局，并能调通健康检查接口。
- **测试**：Testcontainers MySQL 上下文启动测试；全局异常处理测试。

### M1 学习空间 + Subject【R1】

- **后端**：`learning_space`、`subject` 两张表及增删改查；`ai_profile` 的取值先用固定的 `generic/math/cs408` 列表（M4 改为从 PromptRegistry 读取）；Subject 的同空间校验、被引用时禁止删除（引用检查接口先定义，M2/M3 再实现）。
- **前端**：`/spaces` 页面；空间切换器；URL 中带 `spaceId`；空间设置页（基本信息 + Subject 管理）。
- **验收**：创建「数学一」（高数、线代、概率）和「408」（四门课）；切换空间时 URL、颜色和标题都跟着变化；刷新后仍停留在当前空间。
- **测试**：Service 单元测试（名称唯一、归档空间、跨空间的 Subject 被拒绝）；Controller 测试；Repository 集成测试。

### M2 归档 + 文件上传

- **后端**：`archive`、`stored_file` 两张表；`StorageService` 与 `LocalFileStorage`；`FileValidator`（魔数、大小、像素、PDF 检查）；上传（部分成功）、原件读取（Range）、缩略图、PDF 页渲染与缓存、移动、软删除。
- **前端**：资料库页面、归档详情（文件网格）、`FileUploader`（拖拽、多选、粘贴、进度）、文件查看器（图片缩放、PDF 页缩略图条）。
- **验收**：上传手机照片（旋转显示正确）、截图（粘贴）和一份 30 页的扫描 PDF；把 `.exe` 改名为 `.jpg` 上传会被拒绝；可以浏览 PDF 的任意一页。
- **测试**：07 §8 的全部文件测试。

### M3 题目管理

- **后端**：`question`（**包含 4 个复习预留列，但实体不映射、DTO 不暴露**【R5】）、`question_source` 两张表；建题（同空间、来源数量不超过 6、页码有效）、列表筛选（Subject、归档、关键词）、详情、编辑、软删除；实现 `FileReferenceChecker`。
- **前端**：建题向导（来源选择 + 角色 + 排序 + 信息区，暂时隐藏「立即分析」）；错题列表；题目详情（左栏原件查看器、右栏「题目」Tab）。
- **验收**：从 3 张照片建一道题，分别标注题目、我的解答和标准答案；从 PDF 第 5 页建题；被引用的文件无法删除。
- **测试**：建题规则、跨空间来源被拒绝、列表筛选的集成测试；**断言复习预留列存在于表结构中，但没有出现在 API 响应中**。

### M4 AI 分析（单个 Provider）【R2、R6】

- **后端**：
  - `ai.provider`：SPI、`FakeAiProvider`，以及**一个**真实适配器（OpenAI 或 Anthropic，先做手上有 Key 的那家；README C10）
  - `ai.model`：配置绑定、`ModelRegistry`、`ModelCapabilities`、TaskType 能力匹配、`GET /ai/models`
  - `ai.prompt`：`PromptRegistry`（`_common`、`generic`、`math`、`cs408`），记录版本和哈希
  - `ai.input`：`AiInputPreparer`（图片和 PDF 页的缩放与转码）
  - `ai.analysis`：`ai_analysis` 表、异步执行器、结果解析与校验、JSON 修复重试、失败原因记录、启动时恢复，以及完整的可追溯字段
  - 同时建好 `knowledge_point` 和 `question_knowledge_point` 两张表（供 M5 使用）
- **前端**：建题向导中打开「创建后立即分析」和模型下拉框；详情页的「AI 分析」Tab：状态轮询、结果渲染（Markdown + KaTeX）、版本下拉框、模型和 Prompt 信息条、重新分析菜单。
- **验收**：用真实样例跑通「上传 → 建题 → 分析 → 查看」；在同一道题上重新分析 3 次，得到 3 个版本，每个版本都能看到模型和 Prompt 版本；故意让模型输出非法 JSON（使用 Fake），会先修复重试，仍失败时记为 FAILED 并保存原始输出；选择不支持图片的模型会被明确拒绝。
- **测试**：06 §13 的全部测试（使用 Fake）；版本号并发唯一；同一道题同时只能有一个进行中的分析。
- **附带任务**：按官方文档核对并填写所用模型的能力数值。

### M5 确认流程 + 可信度 + 知识点 + 多模型【R3】

- **后端**：可信度计算（信号 + 等级 + `confidence_signals`）；`AnalysisReviewService`（确认、修正、驳回，事务内同时回写 `question` 并关联知识点）；知识点的增删改查、名称规范化、在 Prompt 中注入候选知识点；**接入第二家 Provider**；「以我确认的识别文本为准」重新分析。
- **前端**：可信度徽标和不确定之处列表（点击后左栏跳到对应来源）；确认对话框（采用识别结果、勾选知识点、核对不确定之处）；修正编辑器；驳回；列表中的确认状态和筛选；知识点页（简版）；全局设置页（模型和能力）。
- **验收**：一道低可信度的题目在确认时必须先核对不确定之处；修正后生成 v(n+1)，状态为「用户修正」，原版本变为「已修正」；AI 新提议的知识点不勾选就不会入库；同一道题可以分别用 GPT 和 Claude 分析并对比两个版本。
- **测试**：可信度规则表驱动测试；确认、修正、驳回的状态机测试（包括非法状态转换）；知识点规范化和去重；两个适配器的 WireMock 测试。

### M6 题目级对话

- **后端**：`chat_session`、`chat_message` 两张表；`ContextAssembler`（QUESTION 策略）；`SseEmitter` 流式推送；客户端断开时取消上游请求；消息记录模型、Prompt 版本和上下文快照。
- **前端**：详情页的「对话」Tab：会话列表、流式渲染、停止生成、模型切换、「附带原图」开关。
- **验收**：围绕一道题追问 5 轮，上下文中只包含这道题的内容（查看 `context_snapshot` 验证）；中途换模型后，消息上标注的模型正确；刷新页面后历史还在。
- **测试**：上下文组装测试（确认版本优先、使用 AI 草稿时带标注、历史截断、不包含其他题目）；使用 Fake 的流式测试；取消测试。

### M7 打磨与交付

- 用真实样例做 Prompt 调优（升级为 `v2` 时保留 `v1`），并比较不同模型的效果。
- 单进程打包（前端产物放进 jar）与启动脚本；备份和恢复脚本。
- 修正体验问题：上传速度、详情页布局、公式渲染。
- 同步更新 `AGENTS.md` 和 `docs/`。
- **验收**：连续一周用它记录真实的错题，没有阻塞性问题。

## 3. 各里程碑都要满足的完成标准

- 新增的业务规则都有测试；`mvn verify` 和前端 `vue-tsc`、lint 全部通过。
- 自动化测试中没有真实的 AI 调用。
- 如果架构或行为有变化，同步更新 `docs/` 中对应的章节。
- 没有提交任何 Key；`.env.example` 已更新。

| 顺序 | 功能 | 已有的预留 |

## 5. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 手写公式识别不准 | 分析建立在错误的识别上 | 识别结果单独展示、可以修正；「以我确认的识别文本为准」重新分析；可信度信号；以后加区域框选 |
| 模型自报的可信度不可靠 | 用户过度信任 | 与客观信号结合；未确认的结果一律标为「AI 草稿」 |
| 各厂商的结构化输出能力不一致 | 解析失败 | 按能力选择输出策略；统一在后端校验；修复重试 |
| 能力配置数值有误 | 请求被厂商拒绝或图片被过度压缩 | M4 按官方文档核对；错误信息中带上能力参数，方便排查 |
| AI 成本 | 花费不可控 | 记录每次调用的 token；对话默认不带原图；图片按能力缩放 |
| 范围蔓延 | MVP 延期 | 每个新想法都用 AGENTS.md §19 的主流程来评估；复习和画像只预留字段 |
| 没有登录却暴露到网络上 | 数据泄露 | 默认只监听 127.0.0.1；开放访问前必须先实现访问口令 |
