## D-001 模块化单体，按业务域分包

- **背景**：个人单用户系统；规范禁止微服务。
- **决策**：一个 Spring Boot 应用，分为 `common`、`workspace`、`archive`、`file`、`question`、`ai`、`chat` 和预留的 `auth` 模块；跨模块只能通过 `*Service` 公共方法调用，禁止反向依赖。
- **影响**：部署简单；模块边界要靠约定和测试（可选 ArchUnit）维持。详见 `04-backend-modules.md`。

## D-002 多 AI Provider 架构，厂商 SDK 只用在各自的适配器中

- **背景**：用户要求通过 API 接入 GPT、Claude 等多家模型；原规范只写了 OpenAI Responses API。
- **决策**：业务层只依赖 `AiGateway`；`AiProvider` SPI 按 provider type 分派；首批适配器为 `openai-responses` 和 `anthropic-messages`，在各自的包内使用官方 Java SDK。不使用 Spring AI。所选模型不可用时，不自动切换到其他模型。
- **影响**：新增厂商只需增加适配器和配置。OpenAI 兼容类厂商以后用单独的 `openai-chat-compatible` 适配器接入。详见 `06` §2、§3、§9。

## D-003 模型能力由配置声明，并驱动模型选择和输入预处理

- **背景**：不同模型在图片输入、结构化输出、流式输出和图片尺寸上限等方面差异很大，厂商也没有统一的能力查询接口。
- **决策**：在配置中声明 `ModelCapabilities`（分为协议默认值和按模型覆盖两层），启动时校验；按任务类型（TaskType）过滤可选模型，不满足时提前拒绝，并据此预处理输入、选择输出策略；每次分析都保存能力快照。
- **影响**：能力数值需要按官方文档人工维护（M4 任务）。详见 `06` §4。

## D-004 单用户、无登录，只监听 127.0.0.1

- **背景**：用户确认暂不考虑登录注册，只供个人使用。
- **决策**：MVP 不实现 `auth` 和 `User`（只做设计预留）；设置 `server.address=127.0.0.1`；以后开放局域网或公网访问前，必须先实现访问口令。
- **影响**：加入多用户时，只需给 `learning_space` 增加 `owner_id`。详见 `02` §3、`03` §5.1。

## D-005 在 LearningSpace 下增加可选的轻量 Subject 层

- **背景**：评审意见 R1；原规范提到空间可以有自己的 subjects。
- **决策**：新增 `subject` 表（属于某个空间、不分层级、可停用、可带附加 AI 指令）；Archive、Question 和 KnowledgePoint 可以选择一个 Subject；数据仍然以 `space_id` 为归属主键，禁止跨空间引用。
- **影响**：不设 Subject 的空间不受任何影响。详见 `01` §4.2、`03` §3.2。

## D-006 AI 分析版本化且可追溯，成功结果不可修改

- **背景**：评审意见 R2；规范要求分析可版本化、不覆盖。
- **决策**：`ai_analysis` 每次分析或修正都生成新版本，记录 Provider、模型（配置 ID、请求时的模型名、厂商返回的实际模型）、Prompt 的 key、版本和哈希、Schema 版本、输入快照、用量和耗时；`SUCCEEDED` 版本的内容不可修改。
- **影响**：可以比较同一道题在不同模型、不同 Prompt 下的结果。详见 `03` §3.7、`06` §8。

## D-007 AI 结果需要用户确认，可信度由系统综合评定

- **背景**：评审意见 R3；规范要求 AI 不能假装确定，并允许用户纠正。
- **决策**：分析成功后默认为 `UNREVIEWED`，用户可以确认、修正（生成已确认的 `USER_EDIT` 新版本）或驳回；每道题最多一个确认版本。可信度等级 = 模型自报值结合客观信号，取最低，并保存命中的信号。只有确认过的数据才能用于复习和学习画像。
- **影响**：界面必须清楚区分「AI 草稿」和「已确认」。详见 `01` §5、`06` §7。

## D-008 PDF 页先渲染成图片再发送给 AI；限定 MVP 的 PDF 范围

- **背景**：评审意见 R4；各厂商对原生 PDF 输入的支持不一致。
- **决策**：支持 ≤ 50 MB、≤ 200 页的 PDF；按页浏览；选中的页用 PDFBox 渲染成图片后发送；每道题最多 6 个来源。不支持整份 PDF 分析、框选区域、原生 PDF 输入、提取文字层、加密 PDF。
- **影响**：所有 Provider 行为一致，每页可以单独标注角色。详见 `07` §4。

## D-009 为复习系统预留字段，但不进入 MVP

- **背景**：评审意见 R5。
- **决策**：`question` 表建好 `mastery_level`、`review_count`、`last_reviewed_at`、`next_review_at` 四列，但 MVP 不映射到 DTO、不显示、不写任何逻辑；`review_record` 表只做设计。
- **影响**：以后实现复习功能时不需要改动大表结构。详见 `03` §3.5、§5.2。

## D-010 知识点为扁平标签，新知识点需用户确认后才入库

- **背景**：用户要求知识点可以由 AI 总结，也可以手动创建，并尽量精简。
- **决策**：每个空间内的知识点是扁平标签，按规范化后的名称去重；AI 优先复用已有名称，每题最多 5 个；只有在确认分析或手动添加时才写入关联，AI 提议的新知识点需要用户勾选才会创建。
- **影响**：知识点数量可控；合并功能放到 MVP 之后。详见 `01` §4.8。

## D-011 MVP 范围排除项：AI 拆题、HEIC、局域网访问

- **背景**：用户确认按保守方案处理。
- **决策**：不做 AI 自动拆题（用位置提示代替）；不支持 HEIC（提示转换为 JPG）；不支持手机在局域网内直传；导航中的「AI 助手」「学习画像」显示为禁用；首批接入 OpenAI 和 Anthropic，先接手上有 Key 的那家。
- **影响**：详见 `docs/README.md` C5–C10。

## D-012 异步和流式方案：`@Async` + 轮询、`SseEmitter`，不引入 MQ、Redis、WebFlux

- **背景**：AI 分析耗时 30–120 秒；规范禁止在 MVP 中引入 Redis 等基础设施。
- **决策**：分析用有界线程池异步执行，状态存在数据库中，前端轮询；应用启动时把残留的任务标记为失败。对话用 Servlet `SseEmitter` 流式输出，前端用 fetch 解析 SSE。API 错误统一使用 `ProblemDetail`。
- **影响**：应用重启会中断进行中的分析，用户需要重试。详见 `02` §4。
